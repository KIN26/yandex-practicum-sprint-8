## Стратегия масштабирования и отказоустойчивости

Для обеспечения высокой доступности и отказоустойчивости требуется развернуть приложение в нескольких зонах доступности
и в нескольких регионах, это обеспечит географическую отказоустойчивость и снизит задержку для пользователей из 
разных частей страны, при этом следует использовать горизонтальное масштабирование, оно поможет решить проблему нехватки
вычеслительных ресурсов под нагрузкой

## Конфигурация Kubernetes

Нужно использовать независимые региональные кластеры, этот подход выбран для обеспечения масимальной изоляции отказов.
Этот подход проще в управлении, а также он исключает влияние сетевых задержек между регионами, что позитивно скажется
на пользовательском опыте. Увелечение отказоустойчивости в внутри 1 региона следует проводить путем разворачивания 
на насколько зон доступности.

## Балансировка нагрузки и Geo-Routing

Для балансировки следует использовать GSLB для гео-балансировки между регионами, а что касается балансировки внутри 
кластера следует использовать балансировку на уровне самого kubernetes


## Фейловер-стратегия

Active-Active - это обеспечит высокую доступность, и позволит уложиться в требуемый RTO, так как при стратегии 
Active-Passive есть существенные риски что можно не уложиться в требования, так как поднятие активного кластера займет
больше времени.

## Конфигурация базы данных

Для обеспечения отказоустойчивости и высокой доступности следует распределить базу данных на несколько регионов, по
стратегии Master-Slave, где мастер реплика будет располагаться в 1 регионе и read-реплики в других, так же можно добавить
по несколько read-реплик в каждой зоне доступности, синхронизация между репликами должна использоваться стримминговая
когда из WAL мастер-реплики читаются данные и синхронизируются с read-репликами. Так же в конфигурации базы данных следует
использовать Haproxy для эффективной маршрутизации между репликами БД распределенных в нескольких регионах, pgbouncer 
для эффективного менеджмента пулом соединений, patroni + etcd для обеспечения работы БД без простоев, в качестве хранения
бэкапов будет использоваться S3 хранилище с подходящим для этого тарифным планом, причем снятие бэкапов должно происходить
только с мастера.

## Шардирование БД

Текущий объём данных (50 GB) легко умещается на одной ноде БД. Проблема производительности связана с отсутствием 
реплик для чтения и кеширования. Перед использованием шардирования следует использовать более простые методы такие 
как read-реплики БД и кэширование, на текущем этапе использовать шардирование избыточно
